In this guide, you keep the session in an encrypted cookie with TanStack
Start. The server signs in, refreshes the tokens before rendering, and sends
the signed-in page first, so the browser never shows a "Checking session…"
state or a flash of signed-out content. The browser holds a small client that
mirrors the session, and the
[TanStack Router hooks and guards](/docs/setups/tanstack-router) work with it.
[Server rendering](/docs/server-rendering) explains how the pieces fit.

For TanStack Start in SPA mode, where the browser keeps the session, follow
[TanStack Start in SPA mode](/docs/setups/tanstack-router#tanstack-start-in-spa-mode)
instead. A complete app is in
[`examples/tanstack-start-ssr`](https://github.com/monarcode/session-kit/tree/main/examples/tanstack-start-ssr).

## Before you begin

- Node 22.12 or newer, which Start needs.
- A secret of 32 or more random characters to seal the cookie, set as
  `SESSION_SECRET` on the server. To make one, run
  `openssl rand -base64 32`.

## Installation

To install the packages, run the following command:

```npm
npm install @monarcode/session-kit @tanstack/react-start zod
```

## 1. Create the server engine

`createServerAuth` from `@monarcode/session-kit/server` keeps the session in
a cookie sealed with your `secret`, and refreshes it with your backend.
`startAuth` gives the session of the request Start is handling. Create both
in a server-only module, so Start refuses to bundle it for the browser:

```ts title="src/auth/server.ts"
import "@tanstack/react-start/server-only";
import { createServerAuth } from "@monarcode/session-kit/server";
import { startAuth } from "@monarcode/session-kit/tanstack-start/server";
import { z } from "zod";

const API = "https://api.example.com";

const userSchema = z.object({ id: z.number(), firstName: z.string() });
const tokens = z.object({ accessToken: z.string(), refreshToken: z.string() });

const serverAuth = createServerAuth({
  name: "app",
  user: userSchema,
  secret: process.env.SESSION_SECRET!,
  refresh: async ({ refreshToken, signal }) => {
    const response = await fetch(`${API}/auth/refresh`, {
      method: "POST",
      signal,
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ refreshToken }),
    });
    // The backend rejected the refresh token: sign out.
    if (response.status === 401) return null;
    if (!response.ok) throw new Error(`Refresh failed (${response.status})`);
    return tokens.parse(await response.json());
  },
});

/** The session of the request Start is handling, found on each call. */
export const session = startAuth(serverAuth);

/** Signs in with your backend, from the server. */
export async function login(username: string, password: string) {
  const response = await fetch(`${API}/auth/login`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ username, password }),
  });
  const body: unknown = await response.json().catch(() => null);
  if (!response.ok) {
    // The backend says why, such as wrong credentials, in `message`.
    const failure = z.object({ message: z.string() }).safeParse(body);
    throw new Error(
      failure.success
        ? failure.data.message
        : `Sign-in failed (${response.status})`,
    );
  }
  return { ...tokens.parse(body), user: userSchema.parse(body) };
}
```

[Server sessions](/docs/server-rendering/server-sessions#the-cookie) covers
its other options, rotating the secret, signing out, and the limits every
setup shares.

## 2. Add server functions

`session` finds the request each time it's called, so one object serves
every request. Your server functions decide what the browser may ask for:

```ts title="src/auth/functions.ts"
import { createServerFn } from "@tanstack/react-start";
import { z } from "zod";

import { login, session } from "./server";

export const getSessionFn = createServerFn().handler(() =>
  session.getSession(),
);

export const signInFn = createServerFn({ method: "POST" })
  .validator(z.object({ username: z.string(), password: z.string() }))
  .handler(async ({ data }) =>
    session.signIn(await login(data.username, data.password)),
  );

export const signOutFn = createServerFn({ method: "POST" }).handler(() =>
  session.signOut(),
);
```

`getSession` and `signIn` resolve `{ sessionId, user }`, never tokens, so
their results are safe to send to the browser. Start's compiler replaces each
handler with a request in the browser bundle, and leaves `session` out of it.

## 3. Refresh before rendering

Request middleware refreshes access that is about to expire before any route
or server function reads it, while the response can still set the cookie.
Once Start starts streaming a page, a cookie set later is lost, so a refresh
then, such as in a deferred loader's promise, would spend the refresh token
and drop the new one:

```ts title="src/start.ts"
import {
  createCsrfMiddleware,
  createMiddleware,
  createStart,
} from "@tanstack/react-start";

import { session } from "./auth/server";

const sessionMiddleware = createMiddleware({ type: "request" }).server(
  async ({ next }) => {
    // A failed refresh shows up when a route reads the session.
    await session.refreshIfDue().catch(() => {});
    return next();
  },
);

export const startInstance = createStart(() => ({
  requestMiddleware: [
    createCsrfMiddleware({
      filter: ({ handlerType }) => handlerType === "serverFn",
    }),
    sessionMiddleware,
  ],
}));
```

An app that defines `createStart` has no CSRF protection for its server
functions until it adds `createCsrfMiddleware`. Its `filter` keeps the check
to server-function calls: unfiltered, it also refuses page loads from links
on other sites and from the address bar. Server routes are left out too, so
a server route that changes the session must refuse other sites itself:
compare its `Sec-Fetch-Site` header to `same-origin`.

## 4. Create the browser client

`createMirrorAuth` makes the client that routes and components use. Create it
in `getRouter`, which Start calls once per request on the server and once in
the browser, never at module level. `connectSession` sends the session the
server read to the browser with the page, and runs guards again when it
changes there.

First, the client:

```ts title="src/auth/client.ts"
import { createMirrorAuth } from "@monarcode/session-kit";

import { getSessionFn, signInFn, signOutFn } from "./functions";

export function createAppAuth() {
  return createMirrorAuth({
    name: "app",
    session: null, // filled by loadSession, then by hydration
    revalidate: () => getSessionFn(),
    signIn: (data: { username: string; password: string }) =>
      signInFn({ data }),
    signOut: () => signOutFn(),
  });
}

export type AppAuth = ReturnType<typeof createAppAuth>;
```

Then the Router, which creates it and connects it:

```tsx title="src/router.tsx"
import { connectSession } from "@monarcode/session-kit/tanstack-start";
import { createRouter } from "@tanstack/react-router";

import { createAppAuth } from "./auth/client";
import { routeTree } from "./routeTree.gen";

export function getRouter() {
  const auth = createAppAuth();
  const router = createRouter({ routeTree, context: { auth } });
  connectSession(router);
  return router;
}

declare module "@tanstack/react-router" {
  interface Register {
    router: ReturnType<typeof getRouter>;
  }
}
```

Let TypeScript infer the client's types from its options: with
`createMirrorAuth<User>(…)`, `signIn` would be left out. A `dehydrate` and a
`hydrate` of your own, such as for a query cache, go to `createRouter` as
usual: `connectSession` keeps them.

## 5. Load the session, then guard routes

The root route's `beforeLoad` reads the request's session into the client
with `loadSession`, before any guard runs. In the browser, the hydrated
session is already there, so it doesn't call the server:

```tsx title="src/routes/__root.tsx"
import { loadSession } from "@monarcode/session-kit/tanstack-start";
import { createRootRouteWithContext, Outlet } from "@tanstack/react-router";

import type { AppAuth } from "../auth/client";

export const Route = createRootRouteWithContext<{ auth: AppAuth }>()({
  beforeLoad: ({ context }) => loadSession(context.auth),
  component: Outlet,
});
```

Guards are the ones from `@monarcode/session-kit/tanstack-router`. On the
server, a redirect is a real HTTP redirect:

```tsx title="src/routes/_authenticated.tsx"
import {
  requireSession,
  SessionOutlet,
} from "@monarcode/session-kit/tanstack-router";
import { createFileRoute } from "@tanstack/react-router";

export const Route = createFileRoute("/_authenticated")({
  beforeLoad: ({ context, location }) =>
    requireSession(context.auth, { location, loginPath: "/login" }),
  component: () => <SessionOutlet pending={<p>Loading…</p>} />,
});
```

[Guard private routes](/docs/setups/tanstack-router#3-guard-private-routes)
explains `SessionOutlet`, and an error component for a failed refresh.

Guards decide what a page shows. Server functions that return private data
must check the session themselves, with `session.getSession()` or
`session.credentials.get()`.

## Sign in

The client's `signIn` sends what it's given to your `signInFn`, then adopts
the session it returns, re-runs guards and tells other tabs:

```ts title="src/sign-in.ts"
import type { AppAuth } from "./auth/client";

/** Signs in, and resolves the message to show when it fails. */
export async function signIn(
  auth: AppAuth,
  username: string,
  password: string,
): Promise<string | null> {
  try {
    await auth.signIn({ username, password });
    return null;
  } catch (error) {
    // What signInFn threw, such as your backend's message for a wrong
    // password.
    return error instanceof Error ? error.message : "Could not sign in";
  }
}
```

In a component, `useAuthClient` from `@monarcode/session-kit/tanstack-router`
gives you `auth`, from Router context.

In this guide, the server signs in with your backend, so the user in the cookie
comes from the backend. If the browser signs in with the backend itself, for
example through a provider's SDK, have `signInFn` take the tokens and the user
instead and pass them to `session.signIn`. It seals what it's given: until a
refresh or `updateUser` replaces it, the user in the cookie is what the browser
sent. Use it to show who is signed in, and let your backend authorize requests
with the access token, or check the tokens in `signInFn` first.

## Call your API

On the server, get the access token in a server function.
`credentials.get` refreshes it first when it has expired:

```ts title="src/orders.ts"
import { createServerFn } from "@tanstack/react-start";
import { z } from "zod";

import { session } from "./auth/server";

export const getOrdersFn = createServerFn().handler(async () => {
  const credentials = await session.credentials.get();
  if (!credentials) throw new Error("Sign in first");
  const response = await fetch("https://api.example.com/orders", {
    headers: { Authorization: `Bearer ${credentials.accessToken}` },
  });
  if (!response.ok) throw new Error(`Orders failed (${response.status})`);
  return z.array(z.object({ id: z.number() })).parse(await response.json());
});
```

To call the API from the browser too, with `createAuthFetch` or effetch's
`sessionBearer`, opt in with `clientCredentials: true` in `createServerAuth`.
Expose `session.clientCredentials.get` and `.renew` through two POST server
functions, and pass them as the client's `credentials`. The browser then
keeps the access token in memory, never the refresh token. The example app
does this.

## Things to know

- **Signing out ends the session only with `revoke`.** A copy of the cookie
  works again ten seconds after sign-out: see
  [Sign-out](/docs/server-rendering/server-sessions#sign-out).
- **One session per request.** Each call to `session` reads the request
  Start is handling, and calls during one request share what it read and
  one refresh. Outside a request, such as in the browser, they reject with
  `INVALID_OPTIONS`.
- **Caching.** Pages and server functions that read the session differ per
  user, and Start sends no `Cache-Control` for them. Behind a CDN or proxy
  that caches responses, mark them private, for example with
  `setResponseHeader("Cache-Control", "private, no-store")` from
  `@tanstack/react-start/server` in request middleware, as the example app
  does.
- **Prerendering.** A prerendered page renders at build time, without a
  cookie, so it shows the signed-out state. Don't prerender pages that read
  the session.
- **Tabs.** Signing in or out in one tab reaches the others, which ask the
  server again. So does returning to a tab after a while.
- **More.** Several server instances, the cookie's size, and plain http
  during development: see
  [Server sessions](/docs/server-rendering/server-sessions).
